# Day-ahead solar generation forecast

Hourly day-ahead forecast of AC export for a 10 MW (AC) / 12.5 MWp (DC) fixed-tilt PV plant in Karnataka.
Model inputs are only the day-ahead weather forecast columns and the timestamp.

**Final model: BL50** = 0.5 × physics model + 0.5 × LightGBM correction of that physics model.
- The physics model (B2b) runs: clear sky → forecast-cloud attenuation → plane of array → cell temperature → power.
- The LightGBM model (M2) predicts the ratio of actual power to the physics prediction.

Findings, decisions and validation are logged in `NOTES.md`; the problem statement is in `PROBLEM.md` and `DATASET.md`.

**Results (leakage-safe chronological validation, `experiments/`):** BL50 pooled daylight MAE **274.43 kW = 2.744 % of 10 MW**,
over six forward folds (Jul 2024 – Jun 2025, 3,696 scored daylight hours). Each fold is trained only on data before its
validation window. The test period (Jul–Aug 2025) is never used for fitting or scoring.
- The pooled figure includes the easier dry-season folds. The monsoon folds are higher: F1 (Jul–Aug 2024) 4.31 %,
  F2 (Sep–Oct 2024) 3.51 %. Jul–Aug 2025 should be expected to be worse than 2.744 %.
- It re-measures the frozen production setup (BL50, 15 leaves, 295 rounds, seeds 42–46), which was chosen on the
  earlier folds. It is not a newly tuned model.
- The earlier headline of 3.87 % (mean of folds F1, F2, F8 in `src/validate.py`) came from a validation that is now
  superseded, because it had temporal/data leakage. It is not the reported metric. Details are in `NOTES.md` → `## Leakage-safe validation`.

## Reproduce `predictions.csv`

```powershell
.\.venv\Scripts\python.exe run.py
```

This reads only `data/train.csv` and `data/test.csv`. It runs the cleaning, fits the final model on all training data and writes:
- `predictions.csv` (`timestamp,predicted_ac_power_kw`, 1,488 rows, timestamps exactly as in `data/test.csv`)
- `data/train_clean.parquet`
- `reports/test_sanity.txt`
- the cleaning reports in `reports/`

Expected runtime is about **5 seconds** on a laptop CPU (measured 4 s end to end, including Python start-up). The output is deterministic: repeated runs give a byte-identical `predictions.csv` (fixed seeds, LightGBM `deterministic=True`).

## Code map (`src/`)

- **`audit.py`:** read-only data audit (timestamps, duplicates, sentinels, unit switch, flatlines, soiling, forecast checks).
- **`clean.py`:** the numbered cleaning rules (1–11). Each prints its row counts, flags unusable hours with `train_ok` instead of deleting rows, and builds the soiling-corrected target `ac_power_clean`.
- **`solar.py`:** geometry and the physics chain.
  - Solar position at the hour mid-point.
  - Ineichen clear sky with fitted monthly Linke turbidity, then forecast-cloud factor `1 − a·C^b`, Erbs decomposition, Hay-Davies transposition, Faiman cell temperature, −0.35 %/°C and a fitted loss factor.
  - Also forecast gap filling (`prepare_forecast`).
- **`features.py`:** model features from forecast columns, timestamp and physics outputs only. Includes cloud smoothed within the calendar day and the daily mean cloud; asserts that no measured/status column is used.
- **`validate.py`:** the original (superseded) time-ordered folds (F1/F2 monsoon, F3–F8 rolling monthly) and the metrics: MAE/RMSE % of 10 MW, bias, daily energy error, cloud buckets, skill vs climatology.
- **`train.py`:** baselines (climatology, physics variants), the LightGBM models (`GBMModel`: M1/M2/M3) and the final-choice comparison with its fixed decision rule.
- **`analysis.py`:** post-selection diagnostics: turbidity sensitivity, expected test error, worst days/hours with measured-POA attribution, error by hour.

`run.py` in the project root chains `clean.py` → `solar.py`/`features.py` → the final fit and prediction.

`experiments/leakage_safe_validation.py` is the final, leakage-safe validation of the frozen production setup. It is
isolated from `run.py`: it writes only to `experiments/results/` and never touches `predictions.csv`.
